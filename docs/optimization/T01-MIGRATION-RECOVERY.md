# T01 SQLite 迁移与离线恢复操作说明

计划 V1.0（2026-11-17），仅覆盖 T01。本文件是操作说明；本次没有运行生产 Compose、发布镜像、部署或访问真实 AWS。

## 自动迁移行为

生产默认 DATABASE_URL 为 sqlite:////data/app.db。SQLite 的启动顺序为：获取 BEGIN IMMEDIATE 写锁 → 校验原库 → 创建升级前快照 → 迁移业务表与版本台账 → 校验字段、必需唯一约束、外键定义、integrity_check、foreign_key_check → 同事务提交。只有 init_db 成功，FastAPI 才能 seed 管理员并启动定时收集器。迁移异常向上抛出，启动失败。

新库直接建立当前模型和 schema_migrations 的版本 1；非空且未记录版本的磁盘库先写入同卷 backups/app.db.pre-v1-<随机 ID>.db。备份使用 SQLite backup API，包含 WAL 中已提交的数据，排除未提交事务。版本台账保存 applied_at_utc、backup_path 和 backup_sha256；日志也输出备份路径及哈希，便于迁移失败后的查找。重复启动验证模式，不再备份或改变应用时间。

旧 user_id 唯一凭证表重建时逐列复制所有现有模型字段，包括密文、代理、默认标志、配额和时间戳。只有缺少 is_default 的旧单凭证库补值 1；已有 0/1 不变。旧实例策略/流量没有 credential_id 时，必须能根据面板 user_id 找到恰好一条凭证，原行才绑定该凭证；缺少或多条凭证时停止迁移，不删除记录、不任选一条 Key。历史手动赠金没有归属时增加可空 credential_id，保持 NULL，T03 再处理。

重建时，旧的 `aws_credentials(user_id)`、`instance_settings(user_id,region,instance_name)` 和 `traffic_usage(user_id,region,instance_name,year_month)` 唯一规则按列识别。标准内联约束和标准显式唯一索引得到相同转换：去掉旧单凭证限制，保留模型规定的凭证内唯一性。保留其他可重放的显式索引和触发器。相同列集合但顺序、排序规则或部分索引条件不同，不能当作标准旧键删除。

若重建会丢失额外外键、改变外键动作、`AUTOINCREMENT` 的序列或主键的 rowid 语义，迁移会回滚并停止启动。未知列、额外内联唯一、CHECK/COLLATE/GENERATED/WITHOUT ROWID 等定制定义也需人工核实。未版本化的非空磁盘库已先留下升级前快照。对于**已经登记 v1** 的库，台账结构/版本行不符、仍有上述旧唯一键、必需字段或约束缺失时也会停止；重启不会替你修理旧 v1 或额外生成升级前快照。若旧版本已丢失定制外键或序列，当前库本身不能还原其原义。

遇到上述拒绝：保持服务停止，保全库、侧文件、现有回执与配对镜像；在独立副本上比对升级前备份中的 `sqlite_schema`、外键、索引、`sqlite_sequence`（如存在）、行数和归属。若选择回退，按下文流程同时处理备份之后的合法写入。不要为绕过门禁而删除索引、修写台账或丢弃侧文件。完整性错误或备份失败也停止启动。SQLite URI 选项不支持自动磁盘备份，需在副本验证标准文件 URL。内存库没有持久备份。

## 工具与验证

在本提交 backend 目录中、使用 Python 3.12 执行以下命令。sqlite_backup 模块只用标准库，运行这三个命令不要求 SECRET_KEY、ENCRYPTION_KEY 或 ADMIN_PASSWORD；常规应用启动仍要求原有配置。路径参数使用实际数据库和备份位置，不能照抄占位符。

```bash
python -m app.sqlite_backup backup --database /data/app.db --output /data/backups/manual-before-recovery.db
python -m app.sqlite_backup verify --backup /data/backups/manual-before-recovery.db --sha256 <完整64位SHA256>
python -m app.sqlite_backup restore --backup /data/backups/manual-before-recovery.db --database /data/app.db --sha256 <完整64位SHA256> --offline
```

成功返回 JSON，退出码 0；错误返回 status=failed，退出码 1；缺少命令行参数由 argparse 退出码 2。`backup --output` 应指向受控目录中的**全新独占名称**：目标主文件及同名 `-wal`、`-shm`、`-journal` 必须全部不存在，空侧文件也算占用。遇到残留时改用新的输出名称，并保全原文件组；不要把删除侧文件当作修复步骤。源库可以处于 WAL 模式并继续写入；其他进程不能在发布过程中创建、打开或替换输出文件组。

快照写入暂存文件，完整性检查和 fsync 后以不覆盖的硬链接发布；再按暂存内容的 SHA256 验证发布路径，成功才出回执。POSIX 还同步目录。文件系统不支持硬链接时拒绝备份并停止自动迁移，应先核实卷能力。SQLite backup 最多等待 30 秒；大型库或长时间锁占用触发超时，需在停机窗口验证实际耗时。

`verify` 要求独立快照及完整 SHA256，拒绝任何上述侧文件、哈希不符或完整性错误。它以只读不可变方式打开已封存的快照；`restore` 同样先校验源，再逐字节复制、同步并验证暂存副本。SHA256 必须来自可信交付台账/备份回执，并在异机复制后再次核对。POSIX 备份创建模式为 0600；Windows 的安全性取决于备份目录 ACL，仍需核实生产权限。备份包含凭证密文和用户数据，应与对应加密密钥一起受控保留。

## 升级与回退流程

1. 先在数据库副本验证升级，记录当前数据库文件、卷名、所有访问该库的进程，以及当前前端/后端镜像的不可变摘要；保存配对 Compose 配置和原 ENCRYPTION_KEY。记录候选前后端配对镜像摘要，不能用 latest 作为可追溯回退身份。
2. 进入经授权的维护窗口，停止后端和前端，以及定时任务、调试客户端、备份程序等全部数据库访问进程。确认容器/进程已经退出，禁止 restart 策略或其他编排器在恢复过程中重新启动它们。
3. 使用本提交的独立恢复模块或包含该模块的隔离恢复镜像。恢复容器应 --network none，挂载实际数据库卷，用卷拥有者的 UID/GID 运行。不要启动 uvicorn 或收集器；不需要传入 AWS 凭证或应用密钥。这里没有构建或交付候选生产镜像，实际镜像配对演练留到 T07。
4. 找到与回退版本对应的升级前备份和完整 SHA256。先 verify，再执行 restore --offline。不能仅复制 app.db 忽略 WAL，也不能把升级后数据库直接交给旧镜像当作回退。
5. 恢复会再次核对备份、创建恢复暂存库；若当前目标库可读取，先创建 app.db.pre-restore-<ID>.db 安全快照，包含其已提交 WAL。随后尝试排他锁与 WAL checkpoint，确认侧文件消失后 os.replace 原子替换数据库。在 POSIX 同步目录，保留恢复回执和安全快照哈希。
6. 若目标被占用、仍有 -wal/-shm/-journal、源备份损坏或当前库无法生成有效安全快照，工具拒绝替换。先解决占用/停机问题。对于损坏的当前库，在全部进程已停止后，将原库和所有侧文件一并隔离到新的保全目录，记录清单/哈希，再向空目标路径恢复；不要删除原始材料。工具不自动清理侧文件，也不自动移动损坏数据库。
7. 用 SQLite integrity_check、foreign_key_check 和关键用户/凭证/实例策略/流量记录检查恢复后的数据库，核对预期备份时间和范围。备份之后的合法业务写入不在该快照中；需要业务负责人判断如何从安全快照补回，禁止盲目覆盖或跨用户重新归属。
8. 在恢复数据库检查后，同时恢复对应前端和后端不可变镜像及兼容配置，保持原 ENCRYPTION_KEY。T01 当前模式检查不能保证所有未来版本可降级；旧镜像可能没有模式版本检查，因此镜像配对是硬性流程要求。
9. T06 引入任务表后，回退还必须核对未终结任务及实际 AWS 资源状态，未知结果进入待核实，冲突操作继续禁止，不自动重放。当前版本没有持久任务表，本次未声称执行这部分恢复。确认数据库/镜像/未解决事项均可用后，才由获授权操作者恢复服务并检查健康状态。

--offline 表示操作者确认停机。SQLite 排他锁与侧文件检查能拦截部分占用，不能证明 Linux 上空闲的 DELETE 模式进程已停止；必须独立核对进程/容器。该工具不是在线热恢复机制。
