# 升级与恢复

本应用保持 SQLite、单后端进程和两个容器。数据库升级失败会停止启动，不能忽略失败后继续服务。记录升级前后完整镜像 ID、Git 提交、备份路径与 SHA256，并保留原 SECRET_KEY 和 ENCRYPTION_KEY 的受控副本。本文为操作规程，不代表已执行生产部署。

## 升级准备

1. 停止接受新资源变更，列出排队、运行中、待核对、补偿失败等全部未解决任务及其 AWS 账号、区域、资源、步骤和操作 ID。等待可明确结束的任务；未知写入必须先与 AWS 事实核对。
2. 停止前后端及任何采集、脚本、其他数据库使用者。保留旧前端和旧后端的不可变镜像 ID；仅保留可移动的 tag 不足以回退。
3. 使用候选镜像内的备份工具创建一致性 SQLite 快照，保存工具返回的 SHA256。不要仅复制主 `.db` 文件而遗漏 WAL 中已提交数据。

```text
python -m app.sqlite_backup backup --database /data/app.db --output /data/backups/pre-upgrade.db
python -m app.sqlite_backup verify --backup /data/backups/pre-upgrade.db --sha256 <完整SHA256>
```

4. 将数据库、匹配镜像 ID 和配置引用作为同一恢复点记录。使用新后端执行迁移并检查迁移台账、完整性、历史账单精度、流量整数与策略归属；确认新前端指向匹配 API 后才恢复服务。

## 回退前的任务核对

恢复点之后可能已经接受或执行过新的 AWS 变更。恢复旧数据库并不能撤销 AWS 效果，也不能证明这些任务不存在。

- 停止所有数据库使用者后，导出当前未解决任务清单以及步骤、intent、operation_id 和锁；与恢复点清单做差集。
- 恢复工具会先创建当前数据库的 `pre-restore-…` 安全快照。保留其 SHA256 及任务清单，它可能是恢复点之后未知操作的唯一持久证据。
- 逐项核对两个清单中的未解决操作；确认实际资源身份和结果，避免重放未知写入。核对没有完成时，服务维持停止。
- 旧版本数据库没有持久任务表和资源锁，无法继承新版本锁。启动旧服务会失去应用内保护；不能把“旧库完整性通过”作为恢复正常资源变更的依据。

## 离线恢复

```text
python -m app.sqlite_backup restore --backup /data/backups/pre-upgrade.db --database /data/app.db --sha256 <完整SHA256> --offline
```

保存恢复回执及其中的 `safety_backup`。工具会校验备份 SHA256、SQLite 完整性与外键，拒绝未声明离线恢复，保留当前一致性快照后原子替换目标。`--offline` 是操作者的前置承诺，工具不能自动证明其他容器或进程已经停止。

恢复后同时切回记录中的旧前端、旧后端不可变镜像 ID；在恢复外部服务前复查数据库与任务差集。需要观察旧界面时，只能在隔离环境或另外的写入保护下进行。测试夹具中的写入拦截不是产品内置维护模式。

## 验证范围

T07 的一次性容器演练覆盖 WAL、一致性备份、迁移 DDL 故障回滚、升级前历史策略和账单、备份前后未知任务、恢复安全快照以及两个旧镜像共同启动。正式结果由交接中的固定提交和证据索引确定。真实生产卷 ACL、磁盘满和硬断电不在该演练范围。
